# Shipping updates without rebuilding an APK (Shorebird code push)

MoneyTrack now has the client-side half of **Shorebird** wired in: a
`ShorebirdUpdateService` (`lib/services/shorebird_update_service.dart`) that
checks for and silently downloads patches on launch, and a "Software
updates" card in Settings that shows the installed patch number and lets a
user force a check.

This half of the work only runs code that already ships in the repo. The
other half — registering the app with Shorebird and cutting the first
patchable release — has to happen on a machine with Flutter, the Android/iOS
toolchains, and your own Shorebird account, none of which this session has.
That's what this document walks through.

## What Shorebird actually does

Flutter compiles Dart to native code, so you can't normally change app
behaviour after install without shipping a new build through the Play
Store / App Store. Shorebird patches the compiled Dart code in place: it
ships a small diff that the app downloads and applies on its next cold
start — no store review, no user reinstall.

**What it can patch:** Dart code changes — bug fixes, new widgets, new
screens, business logic, most of what you'll actually be iterating on day
to day.

**What it can't patch** (these still need a normal new release, built and
redistributed the old way):
- Native code changes (new platform channels, native plugin version bumps
  that touch native code, changes to `android/`, `ios/`, etc.)
- New or changed **assets** bundled into the binary (images, fonts) —
  anything in `pubspec.yaml`'s `assets:` section
- A Flutter engine/SDK version bump
- Added plugins that require new native dependencies

In practice: ship features and fixes as patches; do a real release whenever
you touch native code, add a plugin, or change bundled assets.

## One-time setup (run these yourself, locally)

### 1. Install the Shorebird CLI

```sh
curl --proto '=https' --tlsv1.2 https://raw.githubusercontent.com/shorebirdtech/install/main/install.sh -sSf | bash
```

This also installs a pinned Flutter version Shorebird manages for you
(`shorebird flutter`). Full docs: https://docs.shorebird.dev

### 2. Log in

```sh
shorebird login
```

Opens a browser for an interactive login against your own Shorebird
account — this step can't be done from an automated session.

### 3. Initialize the app

From the repo root:

```sh
flutter pub get
shorebird init
```

`shorebird init` registers MoneyTrack as an app on your Shorebird account
and writes **`shorebird.yaml`** to the repo root with a real `app_id`. That
file doesn't exist yet in this repo — it has to be generated by your own
`shorebird init` run, since the app_id only exists once Shorebird's backend
creates it. Commit it once it's generated; it's not a secret, just an
identifier.

### 4. Cut the first release

This is the one you still build and distribute the normal way (Play
Console, direct APK, TestFlight, etc.) — it's what gives every install the
Shorebird engine that later patches apply against.

```sh
shorebird release android      # produces an .aab/.apk under build/
# or, for iOS:
shorebird release ios
```

Install that build on a device/emulator and confirm the "Software updates"
card in Settings now shows **"Base release — no patches installed yet"**
instead of "Not available in this build." If it still says unavailable,
you're running a plain `flutter build`/`flutter run`, not a Shorebird
release — the updater only activates in Shorebird-built binaries.

## Shipping an update from then on

Once that first release is installed somewhere:

```sh
# make your Dart code change, test it locally with `shorebird preview` or
# a normal `flutter run`, then:
shorebird patch android
# or: shorebird patch ios
```

Every install running the matching release picks this patch up automatically:
`ShorebirdUpdateService.checkForUpdate()` runs on next app launch, downloads
the patch in the background, and the Settings card shows "An update has
been downloaded — close and reopen MoneyTrack to apply it." The patch
takes effect on the *next* cold start after download; it's never applied
mid-session.

Useful commands:

```sh
shorebird patches list          # see what's been shipped
shorebird preview               # run a release-mode build with the updater active, without publishing
```

## Notes specific to this integration

- The update check runs once per app launch, fire-and-forget, and never
  blocks the splash screen (see the warning in Shorebird's own docs about
  awaiting `checkForUpdate()`/`update()` during startup —
  `ShorebirdUpdateService` already follows that guidance).
- Patches default to the `stable` track. If you want a beta channel for
  testing patches before everyone gets them, `shorebird patch android
  --track beta` and pass `UpdateTrack.beta` into a future
  `checkForUpdate(track: ...)` call — not wired up yet, since there's only
  one track in use today.
- This session could not run `flutter pub get`, `flutter analyze`, or any
  build step — there is no Flutter/Dart SDK in this sandbox. The new
  Dart code (`shorebird_update_service.dart`, and the edits to `main.dart`
  and `settings_screen.dart`) has been checked by hand and for balanced
  brackets, but **please run `flutter pub get` and `flutter analyze`
  locally before you trust it compiles.**
